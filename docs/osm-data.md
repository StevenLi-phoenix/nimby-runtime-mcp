# OSM 数据与线路几何

[返回主文档 AGENTS.md](../AGENTS.md) · [建线流程](create-line.md) · [默认参数](defaults.md)

## 1. 数据如何进入游戏

```text
OSM relation / way / node
  → 来源快照与站序校验
  → WGS84 经纬度投影为世界坐标
  → 有序线路、站台端点、区间控制点
  → MCP 创建原生蓝图
  → 游戏原生建造检查与扣款
```

OSM 提供地理位置和线路走向，不提供游戏对象 ID、班次、车辆或造价。世界坐标来自地图投影，不是鼠标屏幕坐标；游戏实体由原生命令创建，不修改 OSM、剪贴板或游戏存档。

## 2. 选择 relation 并取完整成员

先核对城市、线路名、运营方向及当前范围。`route_master` 可用来发现子线路；实际几何取相应 `route`。成员可能包含 stop 节点、platform 对象和轨道 way，不应把所有成员当成线路中心线。参见 [OSM route 数据约定](https://wiki.openstreetmap.org/wiki/Relation:route)。

仓库示例来源：

| 用途 | Relation | 本地准备脚本 |
| --- | --- | --- |
| 一号线八通线已使用方向 | [1667140](https://www.openstreetmap.org/relation/1667140) | `prepare_geometry.py` |
| 二号线总关系 | [414866](https://www.openstreetmap.org/relation/414866) | 用于查找内外环子关系 |
| 二号线内环 | [1667236](https://www.openstreetmap.org/relation/1667236) | 核对方向 |
| 二号线外环 | [1667237](https://www.openstreetmap.org/relation/1667237) | `prepare_line2.py`，以此几何构建双线 |

可以只读请求 `GET https://api.openstreetmap.org/api/0.6/relation/<id>/full.json`，保存原始响应。`full` 不会递归展开所有子 relation 的完整几何；发现 route 子关系后应单独获取。大批量数据应使用适当的数据提取服务，避免反复请求编辑 API。接口格式见 [OSM API v0.6](https://wiki.openstreetmap.org/wiki/API_v0.6)。

新下载缓存放 `%TEMP%`，文件名含线路／relation ID，不另建临时目录。记录 URL、抓取时间、relation ID／版本及数据摘要。仓库现有准备脚本仍从 `work/osm-*.json` 读入，这是旧的固定路径；为新线路编写入口时明确输入路径，不假定脚本会自动下载。应保留的可复现规划写入 `data/<line>_plan.json`。

## 3. 连通性与站序

1. 按 `(type, id)` 建对象索引；不同类型的相同数值 ID 不是同一对象。
2. 提取相应方向的轨道 way。与站台有关的 way 不应混入轨道链。
3. 逐段拼接节点：当前末节点等于下一 way 首节点则接入，等于其末节点则反向接入，并去掉重复连接点。
4. 发现断点、多分支或重复绕行时报告具体 way，不用一条长直线填补。简单成员顺序算法不适用于所有 relation，需要按图连通关系和方向处理。
5. 环线最终节点应等于起点。重复的首站只保留一次停站，轨道闭合点仍保留；环线插值用里程取模。
6. 从 stop 成员取得站名和位置，和事先确认的完整站序逐一比较；名称归一化规则显式记录。不能只验证站数相等。

`prepare_line2.py` 的已用输入包含 18 个唯一停站、两条连续轨道 way；生成 192 个线路点，投影总长约 30,208 世界米。这是该快照的结果，不是其他线路的固定数量。

`prepare_geometry.py` 用最近轨道节点定位站点，误差超过 30 世界米便报错；`prepare_line2.py` 要求 stop 节点直接出现在轨道节点序列。这些是示例脚本假设。新数据若只有站房／站台多边形，需要明确选取停站位置并投影到轨道段，不能直接套用站房中心。

OSM 并非实时运营公告。关站、停用、延伸和更名需结合运营方资料与用户指令。保留地理设施和安排运营停站是两件事；例如用户移除的停站不能因为旧 OSM／旧计划仍含该站而自动恢复。

## 4. 投影、长度和站台方向

现有脚本的球面 Web Mercator 投影：

```python
R = 6378137.0
phi = math.radians(latitude)
x = R * math.radians(longitude)
y = R * math.log(math.tan(math.pi / 4 + phi / 2))
```

输入是 OSM WGS84 经纬度，不直接混用其他地图坐标系。`x/y` 是传给 MCP 的世界坐标；OSM ID 与游戏 native ID 分开存放。

局部比例约为 `scale = 1 / cos(phi)`。实际米长度 `L` 生成端点时使用世界长度 `L * scale`。北京附近比例约 1.30，故 30.2 千世界米对应约 23 千实际米。不要把投影折线长度直接当现实里程、游戏票价里程或保证的工程账单。

沿轨道累加相邻点欧氏距离得到世界里程 `chainage`。在车站里程前后各 100 世界米插值，取得单位切向量 `t`；140 实际米站台端点为：

```text
half = 70 * scale
start = station_xy - half * t
end   = station_xy + half * t
```

一号线旧准备脚本生成 120 米站台规划，由其建线脚本再乘 `7/6` 扩为 140 米；二号线计划直接生成 140 米。不要对二号线或新计划重复扩长。紧弯、跨线换乘或狭窄区间需要检查切线和站台余量。

## 5. 区间几何与层级

保留站台端点与原生引出端点；从两个车站之间的线路点中选择控制点。现有建线脚本在每站附近留 `160 * scale` 世界米间距，用 Ramer–Douglas–Peucker、容差 8 世界米简化区间，跳过离当前端点不足 40 世界米的中间点。这些是示例规划参数，不是游戏硬限制；弯道、障碍和短站间应另行检查。

地铁按实际地面／高架／地下区间还原，高铁默认 `1`，普速 `0`，详见默认参数文档。地铁保留每段 `bridge`／`tunnel`／`layer` 来源及转换依据；建筑通道不当作地下隧道，用户确认清河站为高架。几何简化不得丢失桥隧分界；已生成的粗粒度蓝图须检查是否需要补充分界控制点，不能把整条长边抬高冒充短桥还原。

几何相交并不建立拓扑连接。区间必须接到原生端点 ID；同一换乘站的站台轨道通过 Track properties 指向同一 station，不要求附加站外步行连接或 footprint 建筑；折返应构造实际可走的道岔路径。最终以游戏建造检查和行驶验证为准。

普通同层渡线可用于折返／联络配线；跨线正线交叉须检查层级和实际进路，避免信号阻塞，不能只凭二维投影相交或不相交判断。

## 6. 规划文件与来源标注

新线路计划至少包含：

- `source`、`attribution`、抓取信息、范围说明、投影定义和线路类别。
- 有序 `stations`：站名、OSM ID、经纬度、世界坐标、里程、站台长度、端点、最终 depth。
- 有序 `route`：OSM ID、世界坐标、最终 depth；需要追溯时保存原始桥隧标签。
- 环线 `closed`、总站数、里程校验结果，以及用户批准的例外。

这是新规划的完整性要求；现有两个示例 JSON 不一定含全部来源元数据。游戏 ID、命令结果和建成状态放建设检查点，不能写回 OSM 字段冒充来源事实。

保留“© OpenStreetMap contributors”和来源链接；公开分发地图／派生数据时按 [OpenStreetMap 版权与 ODbL 说明](https://www.openstreetmap.org/copyright)提供相应归属和许可信息。


## 玩家几何偏好的应用

- 保持已调整站台的位置和方向，优先成对移动相邻双线的区间控制点，使轨道自然接入站台。
- OSM 局部小弯折不必逐点复刻。若相邻控制点形成反复偏转，沿主走向调整位置，减小局部折线转角，同时保留真实的大弯道及桥隧边界。
- 保持双线平行、间距稳定；不要仅为贴近来源节点而增加小幅 S 弯，也不要以增加节点或改变层级代替平面曲线优化。
- 几十至约百世界米的局部控制点移动可以作为平顺方案候选，但不是统一误差容限。逐处检查地形、道路、跨线交叉和站台接入。
- 控制点折线角仅用于筛查，不等于原生曲率或限速；最终核对游戏曲线和列车运行。
